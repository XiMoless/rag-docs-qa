# 改进方向清单（按性价比排序）

> 全部条目都对着实测数字写，**「预期」列是估计值，不是承诺**——任何改动都必须跑一遍评测再进 `RESULTS.md`，不许凭感觉写收益。
> 当前基线（E004 / E005）：R@5 0.522（v1）/ 0.586（240 题）｜正确率 0.582 / 0.602｜改写题 R@5 **0.312**｜多跳题 R@5 0.375（v2 0.618）但 acc 只 0.458｜弃答率 27%｜幻觉率 2.0%｜P95 4.81s。

---

## 第一梯队：便宜、见效快、简历好讲（1~2 天）

### 1. 邻接 chunk 扩展（small-to-big）
- **证据**：D 段 8 条弃答**全部**是因为同一页被切成相邻 chunk、两题各拿一半（`skills#007` 进了 D-004 的 top-5，D-003 只召回 `skills#008`）。也就是说答案在库里，只是被切断了。
- **做法**：`ask.py` 检索后，对每个命中 chunk 按 `order±1` 取同页邻居并入上下文（不参与打分，只进 prompt）；或做 parent-doc 两段式索引。
- **成本**：约 2 小时，不需要重建索引（`chunks.jsonl` 里已有 `order` 与 `doc_id`）。
- **预期**：单跳/多跳一并涨，弃答率下降；这是当前**最直接**的漏洞。

### 2. 用 bge-m3 的 sparse 向量替换 BM25 通道
- **证据**：中文提问 × 英文语料，BM25 R@5 只有 0.185，这一路是净负担；RRF 等权融合比纯向量低 7.6pp（0.370 vs 0.446），就是被它拖的。
- **做法**：`FlagEmbedding` 的 `BGEM3FlagModel` 一次前向同时出 dense + sparse + colbert，sparse 用 RRF 或加权融合进来。
- **成本**：半天（索引要重建一次，约 5 分钟）。
- **预期**：改写题（R@5 0.312）和标识符题同时受益；如果 fusion 权重调得好，能把 R@5 抬到 0.55~0.60 量级——**必须实测**。

### 3. 加权重 fusion + 「通道有效性」门控
- **证据**：RRF 等权融会把弱通道噪音带进来。已知 BM25 在中文查询上无效。
- **做法**：按查询语言/是否含 ASCII 标识符动态选通道（纯中文口语 → 只用 dense+sparse；含 `put_writes` 这类标识符 → 打开 BM25），或给 RRF 分配权重。
- **成本**：半天，且能写一个「通道选择」的消融行。

### 4. 多跳题生成端专项（E006）
- **证据**：v2 多跳 R@5 0.618（比 v1 高 24pp），但 acc 只 0.471——**瓶颈已经从检索转到生成**。
- **做法**：见 `docs\多跳改进方案.md`——分步引用（先列各片段要点再合成）、数字/标识符落点校验、上下文重排（把两段相关材料放相邻位置）。
- **成本**：1 天，判定标准已提前写死（多跳 +≥5pp、单跳 −≤2pp、无答案保持 20/20、P95 ≤8s）。

## 第二梯队：补严谨性，让数字站得住（2~4 天）

### 5. 240 题的幻觉审计（目前只做了 v1 100 题）
- 现状：`RESULTS.md` 里 E005 的幻觉率列写的是「未做人工审计」。**这是简历里唯一可能被追问「你这个数哪来的」的地方。**
- 做法：4 个审计 agent 各 60 条，用现有 `src/aggregate_audit.py` 汇总。
- 成本：约 1 小时机器时间 + 人工回看 2 条 HALLUC。

### 6. judge 与人工的一致性校准
- 证据：judge 正确率 0.582，人工 OK 率 71%——两个口径差 13pp，面试官会问「到底哪个是真的」。
- 做法：从 240 题里抽 60 条，同时有 judge 分和人工判定，算 Cohen's kappa / 混淆矩阵，然后要么调 judge prompt，要么在文档里明确「judge 只用于同配置横向比较」。

### 7. 加一类「无答案但相关」的题
- 现状：无答案题都是「问库里完全没有的东西」（LlamaIndex、vLLM 参数），模型拒答 20/20 很轻松。
- 更难的现实场景：文档讲了这个主题但没给具体值（比如「bge-m3 的 max_length 默认多少」——文档提了 bge-m3 但没写参数）。这类题才能测出「知道自己在猜」。
- 成本：半天出题 + 半天标注。

### 8. 成本与延迟台账
- 现状：只有 P50/P95，没有 token 花费、没有每次 query 的美元成本。
- 做法：`eval.py` 里累计 `usage.prompt_tokens/completion_tokens`，按 DeepSeek 价格算每条成本，写进 RESULTS 行。
- 成本：2 小时；**面试时「每条 query 多少钱」是很硬的一问**。

## 第三梯队：从「能跑」到「像个产品」（3~7 天）

### 9. 在线 Demo（作品集刚需）
- 现状：只在本机 `127.0.0.1:7860`，HR 点不到。
- 选项：HuggingFace Spaces（免费但要公开代码）／自购小服务器 + Docker／用 Gradio 的 share 链接（临时）。
- **注意**：语料与索引 160MB 不能进 git，部署要重新跑 fetch+ingest+index（约 5 分钟，需网）。

### 10. 多轮对话
- 现状：单轮。真实文档问答第二句就开始「那它和 store 有什么区别？」这种指代。
- 做法：保留最近 N 轮 + 指代消解改写查询（`rewrite(query, history)`），并加一类多轮评测。

### 11. 流式输出
- 现状：生成一次吐完，P50 3.32s 全在等。`stream=True` + Gradio 的 `yield` 即可，体感差异很大。

### 12. 语义缓存与限流
- 清单 §5 把语义缓存列为「可砍」，但它实际是**成本**大头：相同/近义问题重复调 API。
- 做法：query embedding 相似度 >0.95 命中缓存，命中率与省下的钱都记进 RESULTS。

### 13. 工程化
- 无单元测试、无 CI、无 Dockerfile。至少补：`ingest`/`eval` 的 smoke test + GitHub Actions 跑 `validate_eval`（不需要 API key 的部分）。

### 14. 语料扩展与去重
- 现状缺陷：Python/JS 双份文档互相挤占 top-5（已在 README 局限里）。加语言过滤（按 query 语言选侧）或近重复 chunk 去重，能直接抬 MRR。
- 也可扩到第二、第三个文档库（LlamaIndex / vLLM），验证「换库还成立吗」——这比在同一个库上调参更有说服力。

---

## 如果只做三件事

1. **邻接 chunk 扩展**（2 小时，堵住 8 条弃答暴露的漏洞）
2. **sparse 向量替换 BM25 + 通道门控**（1 天，直接打改写题 0.312 的痛）
3. **240 题幻觉审计 + 成本台账**（1 天，让已经有的数字都站得住）

这三件做完，R@5 与正确率都应该有可见提升，且**每一条都能在 RESULTS.md 里找到对应行**——这才是简历上敢写、面试敢让人追问的状态。

## 执行记录（第一梯队）

### ① 邻接 chunk 扩展 —— 已完成（E006 / E007）

结论见 `results/RESULTS.md` 的「E006/E007 分析」：交错排列 +3.8pp 但出现 4 条 1.0→0.0 硬回归；改成**锚点优先 + 邻居标注**后 0.582 → **0.652（+7.0pp）**，P95 4.81s → 5.18s。

### ② 词法通道修复 —— 改方案（不装 FlagEmbedding，改查询翻译）

原计划用 bge-m3 sparse 替换 BM25，**决定不做**，理由：
- `FlagEmbedding` 会拉进 `datasets`/`peft`/`fsspec` 一串传递依赖，和现有 `transformers 5.24.1` 有冲突风险；为了一个通道的修复把整个环境搞坏不划算。
- 更根本的是：**BM25 失效的根因是中英错配，不是 BM25 这个算法**。用一次便宜的 DeepSeek 调用把中文问题翻成英文关键词（`src/query_expand.py`，结果缓存到 `tmp/qe_cache.json`），直接验证了这一点：

| 检索通道 | 中文原查询 R@5 | 翻译后英文查询 R@5 |
|---|---|---|
| 纯 BM25（100 题） | 0.185 | **0.500** |
| MRR | 0.124 | **0.342** |

也就是说：词法通道本身没问题，是「中文问 × 英文语料」让它看起来像个坏通道。分题型看，翻译后 BM25 在改写题上 0.562、单跳 0.558，已经接近纯向量的 0.446。

**这个发现要单独讲**：当初 E102 的结论「BM25 通道失效」是对的，但归因错了——不是「BM25 不适合中文」，而是「BM25 没拿到能匹配的语言」。修正归因后，通道门控（③）的必要性也下降了：翻译后的 BM25 是有信息的，不需要把它关掉。

### ③ 通道门控 —— 测了，不需要（E009 之后的 dry-run）

假设「词法通道在污染融合」，于是给 RRF 加通道权重，把词法压到 0.5：R@5 0.543 → **0.478**，MRR 0.388 → 0.358。**压低词法只会更差**，说明翻译后的 BM25 是有信息的。门控这条不做。

### ④ 多跳生成端 —— 两个方向都试过（E009 证伪、E010/E011 部分有效）

- 提示词加「先逐片段列要点再合并」：acc 0.739 → 0.668（**负结果**，答案长度 +59%，judge 评的是结论不是过程）。
- 加大证据窗口（k_context 5→8→12→16）：0.739 → 0.772 → 0.799 → 0.772。**但重复跑同配置差 2.7pp**（E011 0.799 vs E013 0.772），所以只有 5→8 的 +3.3pp 勉强算，8 以上一律当噪声。

### 第一梯队收口结论

| 项 | 结果 | 能不能进简历 |
|---|---|---|
| 邻接 chunk 扩展 | +7.0pp（E004→E007） | 能（2.6 倍噪声） |
| 词法通道修复（改方案：查询翻译） | +8.7pp（E007→E008），通道级 R@5 0.185→0.500 | 能（3.2 倍噪声） |
| 通道门控 | 负结果，不做 | 不写 |
| 多跳生成端 | 提示词负结果；窗口加大 ≈ 噪声内 | 只写「多跳仍是瓶颈」 |

**下一步（第二梯队）**：240 题上的幻觉审计、judge 与人工一致性校验、加「无答案但相关」题、成本台账（token 已开始记录）。另外 `src/eval.py` 应该加 `--repeat N` 取均值，否则后面所有小于 3pp 的比较都没意义。

## 执行记录（第二梯队）

### ⑤ 240 题幻觉审计 —— 已完成（E015，8 份材料分工）

- 工具：`src/split_audit.py` 切 8 份材料（各 30 条）→ 8 个子 agent 独立判定 → `src/aggregate_audit240.py` 汇总到 `results/hallucination_summary_240.md`。
- 结果：OK 213 / 弃答 22 / 幻觉 5 / 错答 0；**幻觉率 2.1%（guarded）、2.3%（strict）**；弃答率 **9.2%**；人工正确率 88.8%。
- 与 100 题审计（E004 配置）对比：弃答率 27% → 9.2%（降三分之二），幻觉率 2.0% → 2.1%（没降）。**结论：改进压的是「答不出」，不是「编造」。**
- 5 条幻觉：4 条跨语境套 API（JS 参数搬 Python、HITL resume 当崩溃续跑、`configurable` 当运行时配置、自称片段截断实为续页）+ 1 条假否定（断言「没有任何片段命名」而片段里就有）。
- 口径争议留档：v2-H-003 若把「同页邻接块」也算片段，会从 MISS 翻成 HALLUC；v1-C-015 同理。已在逐条 reason 里注明。

### ⑥ judge 与人工一致性校准 —— 已完成

- 100 题那轮：judge 0.582 vs 人工 OK 0.685 → **judge 偏低 10.3pp**。
- 240 题这轮：judge 0.761 vs 人工 88.8% → **偏低 12.7pp**，偏差方向一致、幅度随题量变大。
- 成因：judge 对「说法不同但正确」过严（22 条人工 OK 但 judge 0.5），对「半对」过宽（7 条人工 MISS 却拿 0.5）。
- 纪律：对外只报一种口径。简历写 judge 0.761（可复现），幻觉率写人工审计（judge 看不出来）。已写入 `docs/指标口径.md`。

### ⑦ 「无答案但相关」题 —— 已完成

- 12 道 `v3-J-*`（`eval/parts/v3_partJ.jsonl`），全部满足：主题在语料里有 chunk 覆盖、追问的具体事实经全库 `Select-String -SimpleMatch` 验证 **0 命中**。
- 合成 `eval/eval_set_v3.jsonl` = **252 题**（无答案 32 道：20 道「语料完全没有」+ 12 道「主题在、事实不在」），`validate_eval --expect 252` 0 error。
- 靶子举例：`token_limit`（ModelCallLimitMiddleware 只文档化了 call/run 上限）、`checkpoint_ttl`、`stream_limit`、`maxToolConcurrency`（JS）、`BrowserSaver`（JS）、`maxDeferredIssues`。
- **E016 实测（252 题）：12/12 全部正确拒答。** 上下文高度相关（召回的就是 `ModelCallLimitMiddleware`/`ToolRetryMiddleware`/`FilesystemBackend` 这些页），模型仍是先复述片段里真有的参数（`run_limit`/`thread_limit`/`retry_on`），再明确说「没有任何片段出现 `backoff_by_tool`」——没有一条被相关上下文诱导编出参数或默认值。整体无答案 32/32。

### ⑧ 成本与延迟台账 —— 已完成（token 口径）

- 见 `docs/成本.md`：240 题评测实测 `561K in / 100K out`；查询翻译另计 `33K in / 3K out`（题均 137/12）。
- 关键发现：k_context 5→8→12→16 时 token 几乎不变（230K/229K/225K/228K，100 题），因为 `max_chars=6000` 先截断了。**要压成本该调 `max_chars`，不是 `k_context`。**
- 延迟：P50 3.35–3.99s、P95 4.72–6.11s（k=8 配置），E005（k=5）是 P95 5.02s —— 加证据没让延迟变差，因为答案更短、hedge 更少。
