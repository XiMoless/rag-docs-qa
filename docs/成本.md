# 成本台账（token 计量，不含单价）

> 原则：**只记录实测**。单价请按 DeepSeek 官方价目表自行换算，本文件不写金额，避免价格变动后数字失真。
> 数据来源：`results/RESULTS.md` 的 `tokens in/out` 列 + `results/qe_cost.json`。

## 一次问答的成本构成

一次问答 = **1 次查询翻译** + **1 次生成** +（评测时）**1 次 judge**。三段分别计量。

| 环节 | 实测来源 | 每题 token in | 每题 token out |
|---|---|---|---|
| 查询翻译（中文→英文关键词） | `results/qe_cost.json`（240 题实跑） | **137** | **12.1** |
| 生成 + judge（合计） | E010/E011/E012/E013 四行均值 | **~2,280** | **~405** |
| 合计（评测口径） | — | **~2,417** | **~417** |

说明：

- 翻译的 240 题实测总量：`tokens_in=32884`、`tokens_out=2909`，题均 137.0 / 12.1。
- 生成+judge 取 E010–E013 四行（同一配置重复跑）的均值：230K/41K、229K/41K、225K/39K、228K/40K，即 100 题 ~228K in / ~40K out。
- **`src/eval.py` 的 `tok_in/tok_out` 不含翻译调用**（翻译走 `src/query_expand.py`，单独计量后落 `results/qe_cost.json`）。要算端到端成本必须把两段相加，别只引用 RESULTS 那一列。
- 供参考：不跑 judge 的单次问答成本 ≈ 翻译(137/12) + 生成(约 1,100/300) ≈ **1,240 in / 310 out**（生成部分取自 k=8 时单次 `src.ask` 实测）。

## 为什么不随 k_context 线性增长

E010(k=8) / E011(k=12) / E012(k=16) 的 token 分别是 230K / 229K / 225K（100 题）——**加了 8 个片段反而略降**。原因是 `build_context(max_chars=6000)` 早就把上下文截断了，k 再大也只是在候选池里换人。

⇒ 真要压成本，该调的是 `max_chars`，不是 `k_context`。这一条已写进 `README.md` 已知局限。
